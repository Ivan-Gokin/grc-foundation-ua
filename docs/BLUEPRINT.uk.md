# Концепція проєкту (blueprint)

[English](BLUEPRINT.md)

Документ описує, з чого складається проєкт, як влаштовано дані та як їх підтримувати. Він для тих, хто супроводжує проєкт і вносить зміни. Читачам сайту він не потрібен.

## 1. Що це за проєкт

Фундамент для GRC-інженерії в Україні. Проєкт відповідає на два запитання організації, яка будує систему управління інформаційною безпекою (СУІБ):

1. **Які вимоги законодавства та регуляторів до нас застосовні?** Реєстр законів, постанов, наказів регуляторів, стандартів і політик НАТО з фільтром за типом організації, з ланцюгами нормативних актів і коротким описом кожного акта.
2. **Яких заходів СУІБ стосуються ці вимоги?** Відповідність окремих положень (стаття, пункт) заходам ISO/IEC 27001:2022 або NIST CSF 2.0. Результат завантажується як проєкт Положення про застосовність (SoA) або проєкт цільового профілю з порожніми стовпцями для значень параметрів, які визначає організація, і посилань на політики.

Межі проєкту:

- **Лише діяльність в Україні.** Акти і проєкти ЄС ведуться окремим довідковим переліком (`scope=reference`): вони показують, куди рухається українське законодавство, але ніколи не потрапляють до таблиці заходів. Міжнародні договори, учасницею яких є Україна (Угода про асоціацію, Будапештська конвенція, Конвенція 108, Угода про безпеку з НАТО), входять до основного реєстру.
- **Два стандарти рівня організації:** ISO/IEC 27001:2022 (за замовчуванням) і NIST CSF 2.0.
- **Лише СУІБ.** Інтегрована система управління охоплює також якість (ISO 9001), безперервність (ISO 22301) та інші напрями. У них спільна узгоджена структура, але цей проєкт стосується тільки інформаційної безпеки.
- **Рівень систем (етап 2):** NIST SP 800-53 Rev. 5 з українськими базовими профілями. До нього переходимо від результату CSF 2.0 через офіційну відповідність NIST.

Проєкт - відправна точка, а не юридична консультація. Кожен рядок має джерело походження та статус перевірки.

## 2. Структура репозиторію

```
index.html, 404.html       сайт (одна сторінка; 404.html переводить адреси /eli/...)
assets/                    стилі, скрипти, шрифти та локальні копії бібліотек
assets/js/config.js        адреса репозиторію та інші налаштування  <- змінити перед публікацією
content/                   тексти сторінок у Markdown, uk і en: головна, методика, про проєкт, розділи guide/, статті articles/
mappings/*.xlsx            положення актів і їх зіставлення зі стандартами: редагуються вручну
data/*.csv                 решта: джерела, ланцюги, типи суб'єктів, заходи стандартів
data/sp800-53/             дані рівня систем (етап 2)
data/datapackage.json      опис стовпців опублікованих файлів (Frictionless Data Package)
data/meta.json             версія та дата даних, що показує сайт
scripts/validate.py        перевірка даних
scripts/build.py           збирає сайт у _site/ (додає згенеровані файли, див. нижче)
scripts/mapdata.py         читає і записує таблиці зіставлень
docs/                      цей документ
.github/                   процес публікації, шаблони issue і pull request
```

Нічого згенерованого в git не зберігається, тож кожен факт записано в одному місці. Після кожного push у `main` GitHub Actions запускає `validate.py` і `build.py` і публікує `_site/` на GitHub Pages. Збирання додає:

| Опублікований файл | З чого збирається | Для кого |
|---|---|---|
| `data/provisions.csv`, `data/mappings.csv` | `mappings/*.xlsx` | сайт і програми |
| `data/eli.jsonld` | `sources.csv`, `source_relations.csv` | метадані ELI (3.4) |
| `data/grc-foundation-ua.xlsx` | усе перелічене, разом | люди: реєстр, ланцюги і зіставлення з назвами й текстами |

Локальний перегляд: `pip install openpyxl`, `python3 scripts/build.py`, `python3 -m http.server 8000 -d _site`.

## 3. Модель даних

Усі дані зберігаються у файлах CSV у кодуванні UTF-8 без BOM. GitHub показує кожен файл як таблицю з пошуком. Під час завантаження з сайту BOM додається, щоб Excel правильно відкривав кирилицю.

```
sectors ──< applicability >── sources ──< provisions ──< mappings >── controls (для кожного стандарту)
                                 │
                                 └──< source_relations (ланцюги як властивості ELI: based_on, amends, repeals...)
```

| Файл | Один рядок - це | Ключові стовпці |
|---|---|---|
| `sources.csv` | нормативний акт або документ | `id`, `register_no`, `eli`, `scope`, `domain`, `type`, `status`, `binding`, `role`, `description_*`, `concerns_*`, `url`, `last_verified` |
| `source_types.csv` | тип джерела (закон, постанова КМУ, НД ТЗІ, акт ЄС...) | `id`, назви, видавець |
| `sectors.csv` | тип суб'єкта, який обирає читач ("кого стосується") | `id`, `parent`, `group`, `selectable` |
| `sector_groups.csv` | група типів суб'єктів у фільтрі | `id`, назви |
| `applicability.csv` | "джерело X стосується типу суб'єкта Y" | `source_id`, `sector_id`, `basis`, `verified` |
| `source_relations.csv` | ланка нормативного ланцюга | `source_id`, `relation`, `related_id`, `basis_uk`, `source_url`, `confidence` |
| `provisions.csv` (з «Вимог» у `mappings/*.xlsx`) | одна вимога в джерелі (стаття, пункт) | `id`, `source_id`, `ref_uk`, `provision_type`, `applies_to` |
| `mappings.csv` (з аркушів стандартів у `mappings/*.xlsx`) | зв'язок положення із заходом | `provision_id`, `framework_id`, `control_id`, `relationship`, `coverage`, `parameter_uk` |
| `controls_*.csv` | захід або вимога стандарту | `id`, `level`, `parent` |
| `frameworks.csv` | підтримуваний стандарт | `id`, `tier`, `controls_file` |

Опис кожного стовпця є в `data/datapackage.json`. `provisions.csv` і `mappings.csv` у репозиторії не зберігаються: їх збирають з книг xlsx (4.4).

### 3.1 Ідентифікатори

Ідентифікатори постійні. Опублікований ідентифікатор ніколи не перейменовують і не використовують повторно, бо на нього посилаються люди та інші рядки. Якщо ідентифікатор помилковий, залиште його, а виправте інші стовпці.

| Тип джерела | Шаблон | Приклад |
|---|---|---|
| Закон | `ua-law-<номер>-<скликання>` | `ua-law-2163-viii` |
| Указ Президента | `ua-pres-<номер>-<рік>` | `ua-pres-447-2021` |
| Постанова КМУ | `ua-cmu-<номер>-<рік>` | `ua-cmu-518-2019` |
| Наказ Держспецзв'язку | `ua-ssscip-<номер>-<рік>` | `ua-ssscip-75-2026` |
| Постанова НБУ | `ua-nbu-<номер>-<рік>` | `ua-nbu-95-2017` |
| НД ТЗІ / ДСТУ / ВСТ | `ua-ndtzi-<код>`, `ua-dstu-<код>`, `ua-vst-<код>` | `ua-ndtzi-3.7-003-05` |
| Документ НАТО | `nato-<код малими літерами через дефіс>` | `nato-ac-35-d-2002-rev5` |
| Законопроєкт | `ua-bill-<номер>` | `ua-bill-8153` |
| Міжнародний договір | `intl-<організація>-<код договору>` | `intl-coe-ets-185` |
| Акт ЄС | `eu-<reg\|dir\|reg-del\|reg-impl>-<рік>-<номер>` | `eu-reg-2022-2554` |
| Проєкт акта ЄС | `eu-com-<рік>-<номер>` | `eu-com-2025-837` |

Окрім `id`, кожне джерело має `register_no`: номер, який читач бачить на сайті ("№ 181"). Він продовжує нумерацію первинного реєстру, унікальний і ніколи не використовується повторно, навіть якщо акт видалено. Новий акт отримує наступний вільний номер.

**ELI.** Кожне джерело також має `eli`: європейський ідентифікатор законодавства (European Legislation Identifier), схему URI, якою користуються ЄС і більшість держав-членів (стовп I ELI).

- **Акти ЄС** мають офіційний ELI від Офісу публікацій, наприклад `http://data.europa.eu/eli/reg/2022/2554/oj`. Він веде на EUR-Lex.
- **Усі інші** джерела отримують шлях за шаблоном ELI, який будує цей проєкт, відносно кореня сайту: `eli/<юрисдикція>/<орган>/<вид>/<рік>/<номер>`, наприклад `eli/ua/vru/law/2017/2163-viii`, `eli/ua/cmu/resolution/2019/518`, `eli/ua/ssscip/order/2026/75`. Офіційного ELI в Україні поки немає, тож ці ідентифікатори **неофіційні**, і на сайті їх позначено зірочкою. Коли з'явиться офіційний український ELI, замініть значення стовпця, а `id` залиште.
- Повний IRI - це адреса сайту плюс шлях (`https://ivan-gokin.github.io/grc-foundation-ua/eli/ua/vru/law/2017/2163-viii`). `404.html` переводить такі адреси на акт у реєстрі; `/ukr` чи `/eng` у кінці (мовне вираження) ведуть туди ж.

| Юрисдикція / орган / вид | Для чого |
|---|---|
| `ua/vru/law`, `ua/vru/bill` | закони, законопроєкти |
| `ua/president/decree` | укази Президента (номер без `/рік`) |
| `ua/cmu/resolution`, `ua/nbu/resolution` | постанови КМУ і НБУ |
| `ua/ssscip/order`, `ua/sbu/order`, `ua/moj/order`, `ua/<орган>/order` | накази |
| `ua/nccc/decision`, `ua/ssscip/guidance` | рішення НКЦК, роз'яснення Держспецзв'язку |
| `ua/ssscip/nd-tzi`, `ua/dstu/standard`, `ua/mod/vst` | НД ТЗІ, ДСТУ, ВСТ |
| `int/<сторони або організація>/...` | міжнародні договори, наприклад `int/coe/ets/185` |
| `nato/doc/<код>` | документи НАТО |
| `eu/com/proposal/<рік>/<номер>` | проєкти актів ЄС (офіційного ELI не мають) |

Номер пишеться малими літерами, `/` замінюється на `-`, кирилиця транслітерується (`80/94-ВР` → `80-94-vr`). Частини одного документа отримують підрозділ (`.../2.3-025-24/t1`). `eli` унікальний і такий самий постійний, як `id`.

Ідентифікатор положення: `<source_id>:<локальне посилання>`, наприклад `ua-cmu-373-2006:p7` (пункт 7) або `ua-law-2163-viii:a5-2` (стаття 5, частина 2). Позначки: `p` - пункт, `a` - стаття, `s` - розділ; діапазони й частини через дефіс.

### 3.2 Атрибути джерела, від яких залежить сайт

- **`status`**: `in_force` (чинний), `repealed` (втратив чинність), `not_yet_in_force` (ще не набрав чинності, наприклад договір підписано, але не ратифіковано), `draft` (законопроєкт або проєкт акта ЄС), `unknown`. Нечинні, проєкти і ще не чинні джерела за замовчуванням приховані, але ніколи не видаляються. До таблиці заходів потрапляють лише `in_force`.
- **`scope`**: `core` (законодавство України, міжнародні договори, НАТО) або `reference` (акти і проєкти ЄС на окремій вкладці).
- **`domain`**: `cybersecurity` або `records` (вимоги до діловодства, корисні для інтегрованої системи управління; за замовчуванням приховані).
- **`description_*`, `concerns_*`**: одне-два речення про те, про що акт, і кого він стосується, словами. `comment_uk` містить робочі нотатки автора (стан, зміни, дати).
- **`binding`**: `mandatory` (обов'язковий) або `recommended` (методичні рекомендації, національні стандарти). Читач може приховати рекомендації.
- **`role`**: роль документа з погляду відповідності:
  - `requirements`: містить обов'язки. Його положення зіставляють із заходами.
  - `context`: визначає національну систему, регуляторів, стратегію. Показується для розуміння, не зіставляється.
  - `procedural`: правила процедур самого регулятора.
  - `amending`: лише вносить зміни до інших актів. Зіставляють консолідовану редакцію зміненого акта, а не цей.
- **`text_access`**: `public` або `restricted` (гриф "ДСК" чи НАТО INV). Документи з обмеженим доступом наведено, щоб читач знав про їх існування, але публічно зіставити їх неможливо.

### 3.3 Типи суб'єктів і застосовність

Кожен акт позначено типами суб'єктів, яких він стосується (`applicability.csv`). 25 типів у `sectors.csv` згруповано для фільтра (`sector_groups.csv`):

- **правовий статус:** оператори КІ, власники ОКІІ, державний сектор, основні суб'єкти національної системи кібербезпеки, Сили оборони;
- **інформація, яку обробляють:** державні ІР та інформація з обмеженим доступом, державна таємниця, інформація НАТО, персональні дані;
- **галузь або послуга:** фінансовий сектор, електронні комунікації, довірчі послуги, хмарні послуги і ЦОД, цифрові платформи, охорона здоров'я, промислові системи керування, ШІ, оборонна промисловість;
- **постачальники:** виробники ПЗ і обладнання, постачальники ІКТ, надавачі послуг кібербезпеки.

`general` ("усі організації") не обирається: він додається завжди. Акти, що лише визначають державну політику чи процедури регулятора, не мають тегів і мають `role=context`.

Тип може мати кількох батьків (`parent` через `;`). Категорії критичності `cii-1-2` і `cii-3-4` належать і до `ki`, і до `kii`, а `public-sir` / `public-restricted` - і до `state-ir`, і до `public-sector`. Вони потрібні, бо базові заходи Держспецзв'язку застосовуються за категоріями.

Логіка відбору: вибраний тип додає своїх батьків і `general` під час відбору актів (вибір `cii-3-4` показує акти з тегами `ki`, `kii`, `cii-3-4` або `general`). Для положень з `applies_to` широкий тип охоплює і вужчі (вибір `ki` показує базові заходи для обох груп критичності).

### 3.4 Нормативні ланцюги: як не дублювати вимоги

Вимоги часто лежать на кількох рівнях: закон доручає Кабміну, Кабмін - Держспецзв'язку. Ланцюги записано словником онтології ELI, тож ними можна обмінюватися з EUR-Lex і національними офіційними виданнями, що публікують метадані ELI. Щоб не рахувати одну вимогу двічі:

1. Зафіксуйте ланцюг у `source_relations.csv` (`ua-cmu-518-2019 based_on ua-law-2163-viii`), правову підставу в `basis_uk` (зазвичай преамбула: "Відповідно до ч. 3 ст. 5 Закону..."), де її знайдено, в `source_url`, і `confidence`: `high`, якщо взято з самого акта, `medium`, якщо з вторинних джерел. Рядок завжди читається "source_id *відношення* related_id" у напрямку онтології ELI: новіший або нижчий акт є `source_id`. `relation` - властивість онтології ELI 1.5:

   | `relation` | Коли `source_id`... | На вкладці "Ланцюги" |
   |---|---|---|
   | `based_on` | ухвалено на підставі уповноважувального акта (постанова КМУ на підставі закону, наказ на підставі постанови, делегований акт ЄС на підставі базового) | вкладено |
   | `transposes` | наближує або транспонує директиву ЄС | вкладено, з позначкою |
   | `applies` | узгоджується з актом, який не транспонують, зазвичай регламентом ЄС | вкладено, з позначкою |
   | `ensures_implementation_of` | виконує договір, стратегію чи план, не будучи ними уповноважений | вкладено, з позначкою |
   | `amends` | змінює текст іншого акта (зокрема викладає в новій редакції) | поруч |
   | `repeals` | повністю скасовує або замінює інший акт | поруч |
   | `commences` | вводить інший акт у дію | поруч |
   | `cites`, `related_to` | лише посилається на нього або пов'язаний інакше | поруч |
   | `adopts` (ELI-DL) | є законом, ухваленим за законопроєктом (`related_id` - законопроєкт) | поруч |

   Законопроєкт або проєкт акта ЄС (`status=draft`) використовує ті самі властивості для змін, які він пропонує (`ua-bill-8153 repeals ua-law-2297-vi`); сайт позначає їх "за проєктом", а JSON-LD записує як `eli-dl:foresees_change_of`.
2. Визначте тип кожного положення:
   - `substantive`: справжній обов'язок. Зіставляйте його.
   - `delegating`: "порядок встановлює Кабінет Міністрів". Не зіставляйте. Вимогу несуть положення підпорядкованого акта, а ланцюг показує правову підставу.
   - `definitional`: сфера дії, терміни. Не зіставляйте, але можна використати в описі.
3. Коли акт замінено, додайте зв'язок `repeals` від нового акта, позначте старий як `repealed` і зіставте новий.

**Ланцюги для машин.** Під час публікації `scripts/build.py` перетворює `sources.csv` і `source_relations.csv` на `data/eli.jsonld`: кожен акт як `eli:LegalResource` (законопроєкти і проєкти ЄС як `eli:Work`) з ELI, видом, датою, чинністю, видавцем, назвою мовою оригіналу і ланками ланцюгів як властивостями ELI (стовп II). Цей файл у репозиторії не зберігається.

### 3.5 Методика зіставлення

Зіставлення побудовано на моделі множинних відношень з NIST IR 8477 (методика програми OLIR). **Положення - фокусний елемент**, захід - еталонний, тож кожен рядок читається як "положення X є `<відношення>` до заходу Y".

| `relationship` | Значення | Типове `coverage` |
|---|---|---|
| `equal` | Однаковий обсяг і мета | `full` |
| `subset_of` | Положення вужче за захід | `full`: впровадження заходу його виконує |
| `superset_of` | Положення ширше за захід | `partial`: потрібно більше |
| `intersects_with` | Перетинаються, у кожного є частина, якої немає в іншого | `partial` |
| `no_relationship` | Перевірено, зв'язку немає (фіксуємо, щоб показати, що прогалину розглянули). З порожнім `control_id` означає, що положення звірено з усім стандартом і жоден захід його не покриває: сайт показує його серед "вимог без відповідника" | `none` |

Інші стовпці:

- **`rationale`**: `semantic` (зміст), `syntactic` (формулювання), `functional` (результат).
- **`strength`**: необов'язкова оцінка 1-10.
- **`coverage`**: чи повністю виконує положення впровадження заходу? Саме на це орієнтується читач: `partial` означає, що самої СУІБ недостатньо.
- **`parameter_uk` / `parameter_en`**: значення, яке встановлює закон для параметра, що інакше визначала б сама організація: строк зберігання, періодичність перегляду, строк повідомлення. Під час вивантаження це стає "мінімумом за законодавством" поруч із порожнім стовпцем "значення організації". Якщо кілька положень задають різні значення для одного заходу, сайт показує всі, і діє найсуворіше.
- **`policy_uk` / `policy_en`**: внутрішній документ (політика, процедура), куди варто внести вимогу. Це підказка; власне посилання організація вписує в порожній стовпець вивантаження.
- **`review_status`**: `ai_draft` (згенеровано ШІ, людина ще не вичитала), `draft` (запропоновано людиною, не перевірено), `imported` (з попереднього набору даних), `reviewed` (перевірено другою людиною, заповнено `reviewed_by`). У рядків від ШІ поле `mapped_by` також починається з "AI".

**Зіставлення від ШІ.** Вони корисні як перший прохід, але ніколи не стають `reviewed` одразу. Людина звіряє кожен рядок з текстом акта (номер пункту, редакція, відношення, покриття), виправляє, заповнює `reviewed_by` і лише тоді ставить `reviewed`. Сайт показує рядки `ai_draft` з позначкою "ШІ, не вичитано" і попередженням над таблицею, а також позначає їх в усіх вивантаженнях.

Зіставляйте кожне положення з обома стандартами напряму. Не виводьте відповідність ISO з відповідності CSF чи навпаки: неточність накопичується.

### 3.6 Стовпці вивантаження

Сайт вивантажує те, що бачить читач, і додає порожні стовпці для заповнення:

| Стовпець | Хто заповнює |
|---|---|
| Ідентифікатор і назва заходу, правові підстави, відношення, покриття, параметр за законом | сайт |
| Застосовний (так/ні), обґрунтування виключення | організація |

Для ISO 27001 це проєкт Положення про застосовність, для CSF 2.0 - проєкт цільового профілю.

3. Додайте по рядку на кожен тип суб'єкта в `applicability.csv` з полем `basis` (чому застосовний) і `verified=yes`, якщо ви перевірили статтю про сферу дії. Акти без прямих обов'язків тегів не мають і отримують `role=context`.

6. Запустіть `python3 scripts/validate.py` і відкрийте pull request. CI виконає ту саму перевірку, а після злиття опублікує сайт.

### 4.2 Законопроєкти і акти ЄС

- **Законопроєкти** (`type=ua_bill`, `status=draft`) - перелік для спостереження. Включайте законопроєкт, лише якщо він створить обов'язки для організацій і є урядовим, пройшов перше читання або пов'язаний із зобов'язаннями перед ЄС. Тримайте в `comment_uk` "станом на <дата>". Коли закон ухвалено, додайте його новим рядком зі зв'язком `adopts` від закону до законопроєкту, а законопроєкт позначте `repealed`; якщо відкликано - `repealed` з коментарем.
- **Акти ЄС** (`scope=reference`) ведуться за тими самими правилами. Коли Україна ухвалює закон про наближення, пов'яжіть закон України з актом ЄС: `transposes` для директиви, `applies` для регламенту.

### 4.3 Коли акт змінюється

| Подія | Що зробити |
|---|---|
| Внесено зміни | Перевірте, чи змінилися зіставлені положення. У книзі оновіть `Вимога` і `Параметр за законом`, змініть `Статус` зачеплених зв'язків на `чернетка`; оновіть `last_verified` у `sources.csv`. |
| Втратив чинність | `status=repealed`. Рядок, положення і зіставлення залишаються для історії. |
| Замінено новим актом | Додайте новий акт і зв'язок `repeals`, позначте старий `repealed`, зіставте положення нового. |
| Змінилася нумерація пунктів | `Код` не змінюйте (він постійний); оновіть `Пункт` у «Вимогах» і у зв'язках, що на нього посилаються (Знайти і замінити). |

### 4.4 Додавання положень і зіставлень

Положення і зіставлення ведуться в `mappings/*.xlsx`, по одній книзі на групу актів (`nbu.xlsx`, `law-80-94-vr.xlsx`...). У кожній книзі:

- **«Вимоги»**: по рядку на кожну вимогу акта: `Акт` (ідентифікатор джерела), `Код` (короткий постійний код, наприклад `p40`; якщо залишити порожнім, його буде утворено з пункту), `Пункт`, `Вимога`, `Тип`, `Стосується лише`, `Застереження` і необов'язкові англійські стовпці.
- **по аркушу на кожен стандарт**, названому його ідентифікатором (`iso27001-2022`, `csf-2.0`): по рядку на кожен зв'язок: `Акт` + `Пункт` точно як у «Вимогах» (скопіюйте), `Захід`, `Відношення`, `Обґрунтування` і за потреби `Сила`, `Покриття`, `Параметр за законом`, `Куди внести`, `Примітка`, `Статус`, `Хто зіставив`, `Хто перевірив`, `Дата`. `Захід` «—» означає, що в стандарті немає відповідника.

Заголовки стовпців мають примітки, а стовпці з фіксованими значеннями - випадні списки. Порожнє `Покриття` випливає з відношення (subset of / equal = повне, інакше часткове); порожній `Статус` означає чернетку.

- Один рядок - одна вимога. Сусідні пункти об'єднуйте лише тоді, коли вони разом становлять одну вимогу.
- Вимога - коротке власне формулювання, не цитата. Цитуйте акт лише там, де важить точне формулювання.
- Зіставляються лише положення з типом `обов'язок`.
- `Стосується лише` заповнюйте лише тоді, коли положення вужче за акт.
- Для нової групи актів скопіюйте наявну книгу й очистьте рядки. Положення одного акта мають бути лише в одній книзі.
- Не змінюйте `Код` після публікації: це ідентифікатор положення (`ua-nbu-95-2017:el-017`).

### 4.5 Регулярний перегляд

- **Щомісяця:** перегляньте новини Держспецзв'язку та zakon.rada.gov.ua щодо нових або змінених актів у сфері кібербезпеки. Для цього є шаблон issue "Новий або змінений акт".
- **Щокварталу:** відсортуйте `sources.csv` за `last_verified` і перевірте найдавніші чинні рядки. `validate.py --stats` показує кількість неперевірених рядків.
- **Випуск:** оновіть `data/meta.json` (версія, дата), додайте запис у `CHANGELOG.md` і поставте тег (`data-2026.11`). Так на конкретну версію можна послатися.

### 4.6 Переклади

Основна мова даних - українська, англійські назви та описи йдуть за нею. Англійські назви, описи і поле "кого стосується" - неофіційний переклад, який ще треба перевірити. Тримайте терміни узгодженими з глосарієм у посібнику (СУІБ = ISMS, КСЗІ = KSZI, ОКІ = critical infrastructure object). Пишіть «зацікавлені сторони» (interested parties), а не «заінтересовані»; в офіційних текстах, які цитуються дослівно (переклад CSF 2.0 і базові заходи з наказу № 75/2026), залишайте формулювання оригіналу.

### 4.7 Авторське право

- Офіційні документи України (закони, постанови, накази) не є об'єктами авторського права, їх можна цитувати.
- Публікації NIST - твори уряду США, суспільне надбання.
- **Текст ISO захищений авторським правом.** Публікуємо лише ідентифікатори заходів і власні короткі формулювання. Ніколи не вставляйте в дані текст ISO.
- Документи НАТО: наводимо лише те, що доступне публічно. Документи з обмеженим доступом - лише як посилання.

## 5. Як працює сайт

- `index.html` завантажує `config.js`, `i18n.js` і `app.js`, а також дві бібліотеки з теки `assets/vendor/`: PapaParse (CSV) і marked (Markdown). SheetJS (теж локальна копія) завантажується лише тоді, коли хтось вивантажує файл Excel.
- `404.html` переводить ELI-адреси проєкту (`/eli/...`) на акт у реєстрі.
- `app.js` читає CSV з `data/` (два з них зібрано з книг xlsx), будує індекси й показує розділи: **Головна** (`content/home.*.md`), **Опитувальник** (`#/start`: чотири запитання, що задають фільтри і стандарт; відповіді не зберігаються), **Посібник** (розділи з `content/guide/`, перелічені в константі `CHAPTERS` у `app.js`, з меню в шапці і панеллю ліворуч), **Заходи** (один розділ для обох рівнів: стандарти СУІБ ISO/IEC 27001 і NIST CSF 2.0 та NIST SP 800-53 для інформаційної системи), **Нормативні джерела** (вкладки для законодавства України і довідкового переліку ЄС, кожна як перелік або як ланцюги), **Методика** (`content/method.*.md`), **Статті** (Markdown з `content/articles/`, у меню посібника) і **Про проєкт** (`content/about.*.md`; завантаження даних і плани додає `app.js`). Старі посилання `#/system`, `#/data` і `#/guide` працюють. Посилання на кшталт `#/method#id-заголовка` прокручує до заголовка.
- Умовні позначення в Markdown у `content/`: абзац, що починається з **Мета.**, **Результат.** або **Типові помилки** (разом зі списком після нього), показується як виділений блок; рядок курсивом одразу під заголовком - це рядок «Відповідає:».
- Стан (мова, розділ, сектори, стандарт, перемикачі) зберігається в адресі сторінки, тож відфільтрованим виглядом можна поділитися посиланням.
- Нічого нікуди не надсилається. Фільтрація та вивантаження відбуваються в браузері.

Логіка відбору для таблиці заходів:

1. До обраних секторів додаються їхні батьківські та `general`.
2. Джерело потрапляє до вибірки, якщо воно в області `core`, має статус `in_force`, має рядок застосовності для будь-якого з цих типів і (коли рекомендації вимкнено) має `binding=mandatory`.
3. Положення цих джерел потрапляють до вибірки, якщо `applies_to` порожнє або перетинається з обраними типами та їхніми вужчими підтипами.
4. Зіставлення цих положень з обраним стандартом дають "правові підстави" кожного заходу.
5. За замовчуванням показано лише заходи, що мають хоча б одну підставу. Перемикач показує повний перелік заходів для повного SoA.

## 6. Етап 2: рівень систем

Рівень організації (ISO 27001 чи CSF 2.0) визначає, що організація бере на себе. Рівень систем (NIST SP 800-53) - це вибір і налаштування параметрів заходів для кожної інформаційної системи. У розділі «Заходи» варіант «Інформаційна система → NIST SP 800-53» показує для кожного заходу, звідки береться вимога. Джерела описано в `data/sp800-53/profiles.csv`:

| `kind` | Джерело | Як отримано заходи SP 800-53 |
|---|---|---|
| `baseline` | базові профілі безпеки Держспецзв'язку (накази № 409/2025, 419/2025, 843/2025) | напряму: стовпець `<id>` і параметри `<id>_params_uk` у `baselines_ua.csv` |
| `plan` | базові заходи з кіберзахисту - обов'язкова частина плану кіберзахисту (наказ № 75/2026) | підкатегорії CSF з положень цього акта, з урахуванням категорії об'єкта (`applies_to`), розгорнуті через відповідність NIST CSF 2.0 - SP 800-53 (`map_csf-2.0_sp800-53r5.csv`) |
| - | CSF і законодавство | підкатегорії CSF, яких вимагають усі інші акти (зіставлення з `mappings/*.xlsx`), розгорнуті тією самою відповідністю |
| `sector` | галузеві профілі безпеки (ст. 10 Закону № 80/94-ВР) | як `baseline`; поки жодного не затверджено |

Щоб додати галузевий профіль, коли його затвердять: додайте акт у `sources.csv`, рядок `kind=sector` у `profiles.csv` і два стовпці в `baselines_ua.csv` (`<id>` зі значенням `yes` для заходів профілю і `<id>_params_uk` з параметрами). Сайт підхопить його без змін у коді.

Розгортання через відповідність дає надлишковий перелік, тож це кандидати для адаптації, а не остаточний набір. Зіставлення з ISO 27001 сюди не потрапляють. Ще не зроблено: відповідність NIST SP 800-53 - ISO 27001 і вивантаження в OSCAL (машиночитні профілі із заданими параметрами) - міст до автоматизації.

## 7. Перевірки якості

`scripts/validate.py` зупиняє CI, якщо знайде: невідомі стовпці чи значення в книгах xlsx, зв'язок, чиїх `Акт` + `Пункт` немає у «Вимогах», повторений пункт чи код, повторювані чи неправильні ідентифікатори, посилання на невідомі джерела, сектори, положення чи заходи, недопустимі значення переліків, хибні дати чи адреси, BOM у CSV, зіставлення з функцією чи категорією замість підкатегорії чи заходу, перевірене зіставлення без зазначеного рецензента. Також зупиняє, якщо `eli` має неправильний формат чи повторюється, або якщо в `relation` невідома властивість ELI. Попереджає про неперевірені рядки та чернетки зіставлень.
